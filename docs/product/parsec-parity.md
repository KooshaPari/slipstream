# Parsec parity inventory

Status: reference document, written 2026-11-16. Nothing here is a commitment. Most items are
deliberately **deferred** until the streaming core is finished. The point of this file is that the
operator's expectations are written down once, so nothing is silently forgotten and nothing gets
built by accident.

## Confidence

This document was audited against code, not against `docs-site/`. Every `have` or `partial` cell
now carries a provenance tag. Numbers for this revision:

- **Rows total:** 130.
- **Rows claiming `have` or `partial`:** 112.
- **Of those, code-verified (`[v: path:line]`):** 103.
- **Of those, docs-only (`[docs-only]`):** 9.
- **Rows marked `unverified - needs a live host`:** 2 (join latency, mid-session hot-plug). These are
  separate from the 112 because the cell does not claim `have` or `partial`.
- **Rows claiming `none` or `n/a`:** 16 (2 of them carry a `[v:]` citation proving the absence).
- **Downgraded in this pass:** 10 (a `have` became `partial`, a `partial` narrowed to one platform,
  or a claim was reduced to docs-only).
- **Upgraded in this pass (code better than the docs claimed):** 3 (multi-controller count, host-side
  clipboard file policy, macOS client target).

Tag meanings:

- `[v: path:line]` the cited file and line implement the claim on the platform stated. This is the
  only tag that supports `have`.
- `[v: path:line; caveat]` the code exists but is narrower than the row implies (one platform, one
  codec, a gate that must pass). These rows are `partial` even when the mechanism is real.
- `[docs-only]` the only support is `docs-site/content/docs/`. Treat as intent, not capability.
- `[unverified - needs a live host]` a runtime property (latency, negotiation outcome, driver
  behaviour) that cannot be settled by reading source.
- `[downgraded from X]` records what the previous revision claimed.

Two repo doc claims were contradicted by code during this audit, which is why the tags exist:

- The console copy says "Unpair removes trust so the device must pair again to stream"
  (`web/src/sections/Pairing/PairedDevices.tsx:133`), but the Moonlight/GameStream unpair path does
  **not** sever access: `crates/slipstream-host/src/mgmt/clients.rs:79` says the nvhttp TLS layer
  accepts any well-formed client cert, so unpair is listing-only on that plane. The native plane's
  unpair does remove trust (`mgmt/native.rs:206`).
- The Apple client's audio device picker is macOS-only (`#if os(macOS)` at
  `clients/apple/Sources/SlipstreamKit/Audio/AudioDevices.swift:6`). On iOS/tvOS the file compiles
  to nothing, so "client audio device selection" is not an iOS feature.

How to read the rest of the columns:

- **Priority** is about parity with Parsec, not about our own roadmap:
  - `core` = the operator would call the product broken without it.
  - `soon` = expected in the first usable release after core.
  - `later` = nice, real, not now.
  - `dubious` = Parsec does it, but it is not clearly worth copying.
- Parsec facts describe behaviour, not marketing. `verify` means I am not certain Parsec behaves
  that way; `inferred` means I am reasoning from how the product must work; `unknown` means I have
  no figure. Parsec claims are not code-audited here (no Parsec source), only the "Our state"
  column is.
- Parsec has changed shape several times (paid tiers removed for individuals, Teams added, guest
  links and direct IP added and removed and re-added). Treat every version-sensitive claim as
  `verify` unless it is structural.

## Top 10 items I would build first

Ranked by "operator notices immediately if missing", assuming the streaming core is done. This is
parity triage, not the product roadmap.

1. **Per-device revocation and a visible paired-device list.** Trust is the product; a device you
   cannot remove is a device you cannot trust. The list exists; enforcement is uneven.
2. **Reconnect with a visible hold window.** The single biggest felt difference between "remote
   window" and "remote machine", and the mechanism already exists.
3. **In-session overlay with Parsec's item order (displays, mode, bitrate, stats, input mode,
   disconnect).** Muscle memory decides whether the product feels like Parsec.
4. **One error/retry taxonomy with plain sentences.** Cheapest possible reduction in support load;
   currently docs-only.
5. **A compact stats mode that shows fps, Mbps, ms, loss.** The operator will check these numbers
   first and judge everything by them.
6. **Explicit "add virtual display" action with a named output and a stated lifetime.** The most
   requested Parsec power feature, and our display model already supports it.
7. **Host status: who is connected, at what resolution, with a stop button.** The host operator's
   only lever; Parsec is thin here.
8. **4:4:4 on a second encoder family (AMD/Intel, and Windows).** We already have HEVC 4:4:4 on
   Linux NVENC; extending it is the clearest quality win over Parsec.
9. **Per-profile fit/stretch/presentation modes.** Prevents the "why is my ultrawide squashed"
   class of complaint.
10. **Desktop Windows client (or a macOS client target).** Without a desktop client we cannot
    replace Parsec for the operator's own daily use.

## Items we should deliberately not copy

- **Account as a precondition.** Parsec's sign-in is what makes central revocation possible, but
  it also makes the product unusable when the service is down or the account is lost. Our local
  pairing is a feature. If we ever add an account, it must be optional.
- **A friends graph and party system.** It requires an account service, a social trust model, and
  ongoing moderation. Guest tokens and pairing cover the actual need.
- **Teams/enterprise permission matrix as a first-class surface.** Build the per-device capability
  primitive, not the org chart. Teams is a different sale.
- **Paid gating of virtual displays or bitrate.** Never charge by degrading the stream. If we
  charge, charge for scale (hosts, concurrent sessions), not for a second screen.
- **A kernel-mode virtual display driver as the only path.** Our compositor-output approach avoids
  phantom monitors, driver signing, and uninstall residue. Keep the Windows driver optional.
- **A browser client as a parity checkbox.** WebCodecs gives up 4:4:4, low-latency pacing and most
  gamepad fidelity. Reach is not worth claiming parity we cannot deliver.
- **Fire TV and other fragmented TV platforms.** Android TV covers the same users with one codebase.
- **Parsec's "quality" settings surface (raw sliders).** Presets and profile intent are better than
  handing users six numbers and calling it control.
- **Relay-mediated connectivity by default.** It is convenient, but it is also why Parsec needs an
  account and a service. Explicit LAN/VPN connectivity is the honest trade.
- **Silent mode changes.** Parsec sometimes gives you a different resolution than you asked for.
  We already fail loudly instead; keep it that way.
