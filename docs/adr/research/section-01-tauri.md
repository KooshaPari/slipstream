### 2. WEBVIEW2 AVAILABILITY

The Evergreen WebView2 Runtime is a redistributable that serves as the backing web platform for WebView2 apps, conceptually similar to the Visual C++ or .NET runtimes, and "contains modified Microsoft Edge binaries that are fine-tuned and tested for WebView2 apps" (VERIFIED, https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/evergreen-vs-fixed-version).

On Windows 11 the Evergreen Runtime "is preinstalled onto all Windows 11 devices as a part of the Windows 11 operating system". On Windows 10, "Microsoft installed the WebView2 Runtime to all eligible Windows 10 devices", while "a small number of Windows 10 devices don't have the WebView2 Runtime installed" (both VERIFIED, same URL plus https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). That page is explicit that "some devices might not have the Runtime pre-installed, so it's a good practice to check whether the Runtime is present on the client" (VERIFIED, same URL).

Who updates it: Microsoft, not the app. "The WebView2 Runtime updates automatically without requiring any action from you. It receives the same Microsoft Edge updates" (VERIFIED, https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). Evergreen is "recommended for most developers" (VERIFIED, https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/evergreen-vs-fixed-version).

One behavioral detail matters for a long-running management console: the client picks up the new Runtime only on restart. "If your app runs continuously, your app will continue to use the previous version of the WebView2 Runtime", and Microsoft flags "security implications, because the previous version of the WebView2 Runtime might be security vulnerabilities that are fixed in the new version" (VERIFIED, https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). The `NewBrowserVersionAvailable` event is the documented restart prompt (VERIFIED, same URL).

On a clean machine with no runtime and no internet: the Evergreen Bootstrapper "is a tiny (approximately 2 MB) installer" that "downloads and installs the Evergreen Runtime from Microsoft servers" (VERIFIED, same URL). With no internet it has nothing to download. The offline answer is the Evergreen Standalone Installer, "a full installer that installs the Evergreen WebView2 Runtime in offline environments" (VERIFIED, same URL).

### 3. END-USER PREREQUISITES

**Clean Windows 11.** Nothing to install. The Evergreen Runtime is part of the OS (VERIFIED, https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/evergreen-vs-fixed-version).

**Clean Windows 10.** In practice nothing for the user to do on most machines, since Microsoft installed the Runtime on "all eligible Windows 10 devices" (VERIFIED, same URL). For the small number of machines missing it, the documented remedies are to "programmatically deploy the Evergreen Runtime with your app" or to "redirect your end users to the Microsoft site" and have them download the Evergreen Runtime installer themselves (VERIFIED, https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). The offline variant packages the Evergreen Standalone Installer into the app installer or updater (VERIFIED, same URL).

**Windows 10 with no runtime and no internet.** The app cannot start its webview. Tauri offers `webviewInstallMode: "skip"` for this case (VERIFIED, https://v2.tauri.app/distribute/windows-installer/).

### 4. SIZE

Only cited numbers are reported. The Tauri Windows installer page gives the WebView2 install mode deltas: `downloadBootstrapper` adds 0 MB and is the default, `embedBootstrapper` roughly 1.8 MB, `offlineInstaller` roughly 127 MB, `fixedVersion` roughly 180 MB, and `skip` 0 MB and marked not recommended (VERIFIED, https://v2.tauri.app/distribute/windows-installer/). The `webviewInstallMode` enum in the config reference exposes exactly these five variants (VERIFIED, https://v2.tauri.app/reference/config/).

The base application bundle size is UNKNOWN. No official Tauri documentation or official site page states a specific binary or bundle size for a Tauri v2 app, so no figure is asserted here. Upstream asserts only the qualitative claim that Tauri apps "are very small because they use the OS's webview" and "do not ship a runtime since the final binary is compiled from Rust" (VERIFIED, https://v2.tauri.app/start/). That is a direction, not a number.

For the fixed-version path, Microsoft states the Fixed Version binaries "are over 250 MB and will make your app package larger by that amount", and that they "can't be run from a network location or UNC path" (VERIFIED, https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution).

### 5. WHAT SURVIVES OF THE EXISTING WORK

All of it. This is the strongest property of the option.

Tauri is "frontend agnostic and supports most frontend frameworks out of the box", and recommends Vite for SPA frameworks such as React, which is the existing stack (VERIFIED, https://v2.tauri.app/start/frontend/, with a dedicated guide at https://v2.tauri.app/start/frontend/vite/). React 19, Vite 7, Tailwind 4, TypeScript 5.9, Storybook, the orval-generated typed API client and biome all carry over unchanged. The 166 source files and roughly 790 KB of source are untouched.

**Serving the frontend from a local dist build.** VERIFIED. "Conceptually Tauri acts as a static web host. You need to provide Tauri with a folder containing some mix of HTML, CSS, JavaScript and possibly WASM that can be served to the webview Tauri provides" (VERIFIED, https://v2.tauri.app/start/frontend/). The `build.frontendDist` property names that folder, and `tauri build` "makes use of the `build.frontendDist` property from your `tauri.conf.json` file. It also runs your `build.beforeBuildCommand` which usually builds your frontend into `build.frontendDist`" (VERIFIED, https://v2.tauri.app/reference/cli/). The documented config pairs `"devUrl": "http://localhost:3000"` with `"frontendDist": "../dist"` (VERIFIED, https://v2.tauri.app/reference/config/). INFERENCE: the existing Vite output becomes `frontendDist` and the existing `npm run build` becomes `beforeBuildCommand`, so the frontend pipeline needs no change.

**Pointing the webview at the local nitro server.** VERIFIED as possible, and this preserves the existing security architecture. `WebviewUrl::External` takes a parsed URL, and the documented usage builds a window pointed at `http://localhost:{port}` (VERIFIED, https://v2.tauri.app/plugin/localhost/). INFERENCE: setting the window URL to `http://127.0.0.1:47992` keeps the webview on the same origin as the nitro BFF proxy, so the browser's relative `/api/...` calls continue to hit the proxy and the bearer token stays server-side exactly as today.

**Security caveats for loading remote content.** The capability system distinguishes local from remote explicitly. A capability has a `local` boolean, "Whether this capability is enabled for local app URLs or not. Defaults to `true`", and a `remote` property that "Configure[s] remote URLs that can use the capability permissions", which "defaults to not being set, as our default use case is that the content is served from our local application", carrying the caution "Make sure you understand the security implications of providing remote sources with local system access" (VERIFIED, https://v2.tauri.app/reference/config/). INFERENCE: because the default posture denies remote URLs the capability permissions, pointing the webview at `http://127.0.0.1:47992` requires deliberately adding that origin to the capability's `remote.urls` list, and any capability granted to remote URLs must be scoped narrowly.

The default IPC pattern is Brownfield, which "tries to be as compatible as possible with existing frontend projects" and "tries to require nothing additional to what an existing web frontend might use inside a browser" (VERIFIED, https://v2.tauri.app/concept/inter-process-communication/brownfield/). The Isolation pattern is the hardening alternative, and Tauri "highly recommends using the isolation pattern whenever it can be used" (VERIFIED, https://v2.tauri.app/concept/inter-process-communication/isolation/). One constraint matters: "Tauri does not natively support server based alternatives (such as SSR)" (VERIFIED, https://v2.tauri.app/start/frontend/), which is fine because the console is a static SPA talking to a separate nitro server.

### 6. TOKEN INJECTION

The primary answer is that no new mechanism is needed, because the existing arrangement already keeps the token out of the browser.

**Route A, recommended: point the webview at the nitro server.** The webview loads `http://127.0.0.1:47992`, the browser makes same-origin relative `/api/...` calls, the nitro proxy injects the bearer token server-side, and the token never reaches the renderer (VERIFIED for the mechanism's existence, and VERIFIED against repo facts provided by the coordinator for the Slipstream side). INFERENCE: this is a pure URL change plus a capability scope entry, with the BFF token-injection architecture untouched. It is the only route that leaves the existing security posture exactly as it is.

**Route B: the Tauri http plugin.** VERIFIED as officially documented. The plugin "is available in both Rust as a `reqwest` re-export and JavaScript", the JavaScript `fetch` "tries to be as close and compliant to the `fetch` Web API as possible", and Rust gets the re-exported `reqwest` crate (VERIFIED, https://v2.tauri.app/plugin/http-client/). It is permission scoped by URL: the capability grants `http:default` with an `allow` list and a `deny` list, for example `"allow": [{ "url": "https://*.tauri.app" }], "deny": [{ "url": "https://private.tauri.app" }]` (VERIFIED, same URL). The default permission set "enables all fetch operations but does not allow explicitly any origins to be fetched. This needs to be manually configured before usage" (VERIFIED, same URL). Caveat: "[Forbidden request headers](https://fetch.spec.whatwg.org/#terminology-headers) are ignored by default", so injecting an `Authorization` header requires the `unsafe-headers` feature flag on `tauri-plugin-http` (VERIFIED, same URL).

INFERENCE: Route B is strictly more work and strictly more surface than Route A. It needs a different `fetch` in the frontend, the `unsafe-headers` feature, a URL-scoped capability, and it moves the token into the renderer, which is exactly what the current architecture avoids. Its one genuine advantage is that the request originates from the Rust process, so a compromised renderer cannot exfiltrate the token.

**Route C: the Localhost plugin.** VERIFIED as existing and usable. It "Expose[s] your app's assets through a localhost server instead of the default custom protocol", constructed in Rust with `tauri_plugin_localhost::Builder::new(port).build()` and a window built with `WebviewUrl::External(url)` (VERIFIED, https://v2.tauri.app/plugin/localhost/). Official guidance is a caution: "This plugin brings considerable security risks and you should only use it if you know what you are doing. If in doubt, use the default custom protocol implementation" (VERIFIED, same URL). INFERENCE: this serves the app's own assets over localhost and is not needed here, because the nitro server already exists and already is the trusted front door.

### 7. EFFORT TO A POLISHED NON-EMBARRASSING UI

Low, because the existing React UI is reused as-is inside a webview.

**Window chrome and title bar.** Tauri "provides lots of options for customizing the look and feel of your app's window. You can create custom titlebars, have transparent windows, enforce size constraints, and more" (VERIFIED, https://v2.tauri.app/learn/window-customization/). There are three configuration routes, "Through tauri.conf.json", "Through the JavaScript API" and "Through the Window in Rust" (VERIFIED, same URL). The `TitleBarStyle` enum offers `"Visible"`, `"Transparent"` which "Makes the title bar transparent, so the window background color is shown instead", and an overlay variant adding `"decorations"` (VERIFIED, https://v2.tauri.app/reference/config/). The custom titlebar route is documented end to end: set `decorations` to `false`, add window permissions to the capability file (`core:window:default`, `core:window:allow-close`, `core:window:allow-minimize`, `core:window:allow-toggle-maximize`, `core:window:allow-start-dragging`), then style the titlebar in CSS (VERIFIED, https://v2.tauri.app/learn/window-customization/).

**Native theme integration.** VERIFIED. The `Theme` config enum exposes `"Light"`, `"Dark"` and a system theme option (VERIFIED, https://v2.tauri.app/reference/config/).

**Known fidelity gaps.** The documented one is macOS specific: "For macOS, using a custom titlebar will also lose some features provided by the system, such as moving or aligning the window", and the recommended alternative is "making the titlebar transparent and setting the window background color" (VERIFIED, https://v2.tauri.app/learn/window-customization/). A second, non-visual gap: Tauri apps "do not ship a runtime since the final binary is compiled from Rust", so the web platform is whatever the OS provides. WebView2 on Windows and WKWebView on macOS render the same React output through different engines, so CSS feature and form-control rendering differences are possible across platforms. VERIFIED limitation: the Tauri docs flag the Linux path with a dedicated "Linux Graphics Issues" page (VERIFIED, https://v2.tauri.app/develop/debug/linux-graphics/).

INFERENCE: the native window, the taskbar icon and OS-level window management are the actual answer to "a branded native app". The webview renders the existing polished UI with no rework. The remaining visual risk is the custom titlebar strip a native window needs, which is a small amount of CSS against the existing Tailwind design system, not a redesign.

### 9. CROSS-PLATFORM INCLUDING LINUX AND STEAM DECK

**Linux.** VERIFIED. Tauri "requires various system dependencies for development on Linux", with Debian documented as `libwebkit2gtk-4.1-dev` plus `build-essential`, `curl`, `wget`, `file`, `libxdo-dev`, `libssl-dev`, `libayatana-appindicator3-dev` and `librsvg2-dev`, Arch as `webkit2gtk-4.1`, Fedora as `webkit2gtk4.1-devel` (VERIFIED, https://v2.tauri.app/start/prerequisites/). The runtime dependency is confirmed by the bundler: the Debian package specifies "the dependencies `libwebkit2gtk-4.1-0` and `libgtk-3-0`, along with `libappindicator3-1` if your app uses the system tray" (VERIFIED, https://v2.tauri.app/distribute/debian/).

**The WebKitGTK version requirement is strict, with no 4.0 fallback.** VERIFIED from the crate metadata. The `webkit2gtk-sys` crate declares `[package.metadata.system-deps.webkit2gtk_4_1]` with `name = "webkit2gtk-4.1"` and a minimum `version = "2.4"` (VERIFIED, https://crates.io/crates/webkit2gtk-sys, crate tarballs for versions 3.0.0 published 2026-11-19 and 2.0.2). Both declare the same requirement, so the Tauri v1 and v2 lines share the same floor. The wry layer corroborates it, pinning `webkit2gtk = { version = "3" }` alongside `gtk = "0.19"` and `soup3` (VERIFIED, https://github.com/tauri-apps/wry/blob/wry-v0.58.1/Cargo.toml).

**SteamOS and the Steam Deck.** This is where the option is weakest, and the evidence is decisive.

**Tauri itself says nothing about the Steam Deck.** VERIFIED. Across the entire Tauri v2 documentation corpus, both guides and configuration reference, there are zero occurrences of "Steam Deck" and zero of "SteamOS". There is no official Tauri statement of Steam Deck support to cite, so this option's Deck status is defined by runtime dependencies rather than a vendor claim.

**The Steam Linux Runtime does not ship WebKitGTK.** VERIFIED. Across all four Steam runtime branches, `soldier`, `sniper`, `steamrt4` and `steamrt5`, the ABI expectation manifests for `x86_64-linux-gnu` contain no webkit2gtk entry. The `sniper` runtime lists `libgtk-3-0` and `libsoup2.4-1` but no `libwebkit2gtk-4.1-0`; the newer `steamrt4` and `steamrt5` branches ship `libsoup-3.0-0` and no GTK at all. A repository-wide blob search for "webkit" across the `sniper` and `steamrt4` branches returns zero hits (VERIFIED, https://gitlab.steamos.cloud/steamrt/steamrt, refs `steamrt/sniper` and `steamrt/steamrt4`, paths `abi/expectations/x86_64-linux-gnu` and `debian/control`).

**Arch, which SteamOS derives from, does not ship the 4.1 pkg-config either.** VERIFIED. The Arch `webkit2gtk` package is version 2.50.6, depends on `gtk3` and `libsoup`, is built with `-D USE_GTK4=OFF` and `-D USE_SOUP2=ON`, and provides `libwebkit2gtk-4.0.so` rather than a 4.1 soname (VERIFIED, https://gitlab.archlinux.org/archlinux/packaging/packages/webkit2gtk/-/raw/main/PKGBUILD). Arch ships the newer WebKitGTK 6.0 API as a separate `webkitgtk-6.0` package (VERIFIED, https://gitlab.archlinux.org/archlinux/packaging/packages/webkitgtk-6.0). So on an Arch-based host, the pkg-config name Tauri's build probes for, `webkit2gtk-4.1`, is not what Arch provides.

**For contrast, Debian ships exactly what Tauri needs.** VERIFIED. The Debian source package `webkit2gtk` 2.54.3-1 builds both APIs from one source and separates them into distinct binary packages. `libwebkit2gtk-4.1-dev` "depends on `libwebkit2gtk-4.1-0`, `libgtk-3-dev`, `libsoup-3.0-dev`" and its description states it "provides version 4.1 of the API and uses the GTK 3 widget toolkit". The parallel `libwebkitgtk-6.0-dev` "depends on `libwebkitgtk-6.0-4`, `libgtk-4-dev`, `libsoup-3.0-dev`" and is the GTK 4 build (VERIFIED, https://sources.debian.org/data/main/w/webkit2gtk/2.54.3-1/debian/control). INFERENCE: this is the cleanest possible statement of the problem. The 4.1 API that Tauri binds to is a GTK 3 artifact, and it is available as a normal distro package on Debian and Ubuntu but not on Arch or in the Flatpak runtimes.

**The Flatpak route also fails, and this is now settled rather than unknown.** VERIFIED. Tauri's docs do have a Flathub distribution guide (VERIFIED, https://v2.tauri.app/distribute/flatpak/), so the Flatpak path was the obvious workaround. It does not work, for two independent reasons.

First, there is no `webkit2gtk` runtime extension to request. The complete Flathub ref inventory was enumerated from the repository's own OSTree summary, yielding 19,576 refs. The `org.gnome.Platform` namespace has exactly three runtime extensions (`Compat.i386`, `Compat.i386.Debug`, `Locale`) and `org.kde.Platform` has exactly one (`Locale`). The `org.freedesktop.Platform` namespace has 1,409 extensions covering graphics, codecs and Vulkan layers, and none of them is a webkit2gtk extension (VERIFIED, https://dl.flathub.org/repo/summary, the canonical Flathub remote endpoint as published in the `flathub.flatpakrepo` remote config). A full-text scan of all 19,576 refs for "webkit" returns only unrelated applications (`io.github.fastrizwaan.WebkitWord`, `io.qt.qtwebkit.BaseApp`). There is no `org.gnome.Platform.webkit2gtk-4.1` and no `org.kde.Platform.webkit2gtk-4.1`.

Second, the Flatpak runtimes themselves ship the wrong WebKitGTK API. The GNOME runtime is built from `GNOME/gnome-build-meta`, and its WebKitGTK element builds WebKitGTK 2.54.3 with `-DUSE_GTK4=ON`, producing `libwebkitgtk-6.0.so` and `libjavascriptcoregtk-6.0.so` in the devel split, depending on `sdk/gtk.bst`, which is GTK 4.25.1 (VERIFIED, https://gitlab.gnome.org/GNOME/gnome-build-meta/-/blob/master/elements/sdk/webkitgtk.bst and https://gitlab.gnome.org/GNOME/gnome-build-meta/-/blob/master/elements/sdk/gtk.bst). Its libsoup is 3.8.1 providing `libsoup-3.0.so` (VERIFIED, the same repo at `elements/sdk/libsoup.bst`). The webkitgtk element is a dependency of the SDK stack (`elements/sdk-platform.bst`), and the runtime extension manifest for `org.gnome.Platform` (`elements/flatpak/platform/manifest.bst`) declares only the Locale extension alongside the freedesktop GL, VAAPI and codec extensions. INFERENCE: even setting the WebKitGTK question aside, there is no mechanism by which a Flatpak app can reach `libwebkit2gtk-4.1` on a GNOME runtime, because the runtime provides the 6.0 GTK 4 build and ships no webkit2gtk extension.

**What that means for the Deck.** INFERENCE, and a firm one, now resting on complete primary-source enumeration rather than on absence of evidence. A Tauri v2 app cannot be shipped to Steam Deck either as a Steam Runtime title or as a Flatpak. The Steam Runtime ships no WebKitGTK in any of its four branches. The Flatpak route has no webkit2gtk extension to declare and the GNOME runtime ships the 6.0 GTK 4 API rather than the 4.1 GTK 3 API that Tauri binds to. SteamOS is also read-only at the OS level, which the Steam Deck FAQ confirms, so a system-level `libwebkit2gtk-4.1-0` install is not available to the user either. INFERENCE: the only path that would work on the Deck is a Flatpak built against the 6.0 API, which means a wry that has completed the GTK 4 and WebKitGTK 6.0 migration.

**Alternative that avoids the problem.** INFERENCE: if Deck support is required, prefer a webview-free route such as the browser-based Option 7, or wait for the wry-backed GTK 4 and WebKitGTK 6.0 migration that upstream is actively working toward. That migration is real and ongoing: the wry repository has open issue 1767 titled "Migrating to gtk4/webkit6" and issue 1474 titled "Upgrade wry to gtk4-rs and webkit6" (VERIFIED, https://github.com/tauri-apps/wry/issues/1767 and https://github.com/tauri-apps/wry/issues/1474). The evidence above shows why that migration is the decisive unblocker: the 6.0 API on GTK 4 is what the GNOME Flatpak runtime already ships and what Arch already ships, so a wry on WebKitGTK 6.0 would align Tauri with both the Flatpak and Arch worlds rather than against them. INFERENCE: for the Deck specifically, the practical sequencing is to use the browser-based route now and revisit Tauri once wry's GTK 4 migration lands.

## Summary judgement for Option 1

Tauri v2 is a strong fit for the stated goal and a poor fit for the Deck. It reuses 100 percent of the existing React, Vite, Tailwind, Storybook, design-system and orval client work, because Tauri treats the frontend as a static asset bundle served to a system webview and the existing app is exactly that. It gives a real native window with real OS integration, which is what the branding requirement needs, and it does so with one Rust shell crate, one config file and no rewrite of any of the 16 feature sections.

The security story is the decisive technical point. Because the capability model separates local URLs from remote URLs by default, and because the `http` plugin's URL scope is allow-list and deny-list based, the token-injection question has a clean answer: point the webview at the existing nitro server at `http://127.0.0.1:47992` and the bearer token never leaves the server, preserving today's BFF architecture exactly. Using the Tauri http plugin instead would be strictly worse on this axis, since it requires the `unsafe-headers` feature and moves the token into the renderer.

The cost is the WebView2 runtime dependency on Windows, which Microsoft handles automatically on Windows 11 and on nearly all Windows 10 machines. The license is a non-issue, because Apache-2.0 OR MIT covers the framework and the product code is the team's own.

The Steam Deck is the real cost, and it is now settled on primary-source evidence rather than on absence of evidence. Tauri v2 requires `libwebkit2gtk-4.1-0` and `libgtk-3-0`, and the 4.1 API is a GTK 3 artifact. The Steam Linux Runtime ships no WebKitGTK in any of its four current branches. The Flatpak route fails too: there is no `webkit2gtk` runtime extension anywhere in the complete 19,576-ref Flathub inventory, and the GNOME runtime ships WebKitGTK 6.0 on GTK 4 instead. Arch, which SteamOS derives from, provides the 4.0 soname. Debian, by contrast, packages `libwebkit2gtk-4.1-0` cleanly, which is why Tauri works on Debian and Ubuntu desktop. Tauri says nothing about the Deck at all, so there is no vendor support story to lean on.

INFERENCE and judgement: if Windows and Linux desktop are the target platforms, Tauri v2 is the strongest of the native-shell options, and it dominates Option 7 on branding while costing more in runtime dependency and new attack surface. If Steam Deck is a firm requirement, Tauri v2 is not a viable selection today on any of the three distribution routes (Steam Runtime, Flatpak, system package), and the browser-based route is the safer answer for the Deck specifically.
