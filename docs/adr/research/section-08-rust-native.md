## Options 8 to 11: Rust-native GUI toolkits (Slint, egui/eframe, GPUI, iced)

This section evaluates four Rust-native GUI toolkits as replacements for the Slipstream web console, a backend-for-frontend: a React 19 + Vite 7 + Tailwind 4 + TypeScript 5.9 SPA served by a nitro/h3 BFF that proxies to the Rust management API on `https://127.0.0.1:47990` under `/api/v1`, injecting the bearer token server-side. None of the four can reuse any part of that front end. The choice is between four native UI architectures with materially different licensing, Windows maturity, and accessibility stories.

### Slint

**License.** Slint 1.19.1 is triple-licensed: `GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR LicenseRef-Slint-Software-3.0` (VERIFIED, https://crates.io/crates/slint, and the crate's SPDX header at https://raw.githubusercontent.com/slint-ui/slint/master/api/rs/slint/lib.rs).

The Royalty-free edition is a genuine closed-source shipping option, not a trap. VERIFIED from the licensing FAQ and license text (https://raw.githubusercontent.com/slint-ui/slint/master/FAQ.md, https://raw.githubusercontent.com/slint-ui/slint/master/LICENSES/LicenseRef-Slint-Royalty-free-2.0.md): the grant is "world-wide, royalty-free, non-exclusive license to use, reproduce, make available, modify, display, perform, distribute the Software as part of a Desktop, Mobile, or Web Application." Closed-source shipping is allowed. The sole obligation is attribution: display the `AboutSlint` widget in an About screen or splash screen, or place the Slint badge on the public download page.

**Revenue threshold: there is none on the Royalty-free edition.** VERIFIED: the FAQ states "The Royalty-free license is free for desktop, mobile, and web, as long as you show the Slint attribution," with no company-size or turnover condition. The thresholds on the pricing page (50 employees and 10M EUR turnover for Small Enterprise, 10 employees and 2M EUR for Startup, https://slint.dev/pricing) apply to the *paid Commercial* plans only.

**GPL compatibility.** VERIFIED (https://raw.githubusercontent.com/slint-ui/slint/master/FAQ.md): "whichever Slint license you use, your own source files can stay under a permissive license such as MIT or Apache-2.0." GPLv3 forces the *combined work* to be GPL, though your own modules can remain MIT; Royalty-free keeps the product under your own terms. Embedded systems are excluded from Royalty-free and need Commercial or GPL.

**Windows support and prerequisites.** Slint's Windows path is `winit` plus its own renderer, built in by default (VERIFIED, https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backend_winit/). The renderer table (VERIFIED, same URL) is explicit: FemtoVG needs OpenGL; FemtoVG-WGPU supports Metal, Direct3D, Vulkan; Skia supports OpenGL, Metal, Direct3D, and software; `winit-software` is "Software-rendering, no GPU required." Selection tries Skia, then FemtoVG, then software. A clean Windows machine needs no WebView2 and no WebKitGTK. With the Skia renderer the MSVC runtime is needed (VERIFIED, https://docs.slint.dev/latest/docs/slint/guide/platforms/desktop/packaging/windows/), documented as the cause of "The application doesn't start on Windows but exits immediately."

There is no maintained egui backend for Slint: `slint-egui` is not published (VERIFIED, https://crates.io/api/v1/crates/slint-egui returns 404) and its GitHub repo is 404. The upstream backend list holds android-activity, linuxkms, qt, selector, testing, and winit only (VERIFIED, https://github.com/slint-ui/slint/tree/master/internal/backends).



### egui / eframe

**License.** egui and eframe 0.37.0 are `MIT OR Apache-2.0` (VERIFIED, https://crates.io/crates/egui and https://crates.io/crates/eframe; upstream license files at https://github.com/emilk/egui/blob/main/LICENSE-MIT and https://github.com/emilk/egui/blob/main/LICENSE-APACHE). The README confirms "egui is licensed under MIT OR Apache-2.0" (VERIFIED, local `egui_README.md`). This is the cleanest of the four: no attribution obligation, no revenue threshold, no copyleft.

**Windows support and prerequisites.** eframe uses `egui-winit` with `egui_wgpu` or `egui_glow` (VERIFIED, local `egui_README.md`, https://github.com/emilk/egui). The native backend "should work out-of-the-box on Mac and Windows" (VERIFIED, same README). No WebView2 or WebKitGTK: this is a native OpenGL or wgpu window. wgpu "runs natively on Vulkan, Metal, D3D12, and OpenGL" with a DX12 shader fallback to `fxc` (VERIFIED, https://github.com/gfx-rs/wgpu). INFERENCE: on a clean Windows 10/11 machine, a discrete or integrated GPU with a working D3D12 or OpenGL driver is required. There is no documented software-rasteriser fallback in egui/eframe's own materials, unlike Slint's `winit-software` and iced's tiny-skia, so machines with broken or blocklisted drivers are a real deployment risk. The README lists "Native looking interface" as a non-goal and warns "New releases will have breaking changes" (VERIFIED, local `egui_README.md`).

**Accessibility.** This is egui's strongest differentiator. VERIFIED from the README FAQ (local `egui_README.md`): "egui includes optional support for AccessKit, which currently implements the native accessibility APIs on Windows and macOS. This feature is enabled by default in eframe. For platforms AccessKit doesn't yet support, including web, there is an experimental built-in screen reader." The upstream accessibility guide (VERIFIED, https://github.com/emilk/egui/blob/main/docs/accessibility.md) confirms the default-on behaviour, documents `labelled_by` linking and `WidgetInfo` for custom widgets, and notes that `egui_kittest` role-and-label queries test the same tree screen readers consume. This is the best-documented accessibility story of the four on Windows.

### GPUI

**License.** The verified note that the Zed workspace has `publish = false` (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/Cargo.toml, `[workspace.package] publish = false`) needs correction: `gpui` itself is published. VERIFIED from https://crates.io/api/v1/crates/gpui: `max_stable_version` is `0.2.2`, description is "Zed's GPU-accelerated UI framework", homepage is `https://gpui.rs`, repository is `https://github.com/zed-industries/zed`, 573,226 downloads. The crates.io API `license` field is empty for this crate (VERIFIED, same endpoint), so the license comes from the crate's own manifest: `publish = true` and `license = "Apache-2.0"` (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui/Cargo.toml). The published `gpui` crate overrides the workspace default and is Apache-2.0.

**What `publish = false` actually means.** The workspace default applies to crates that inherit it. `gpui_windows` and `gpui_platform` both carry `publish.workspace = true` and `license = "Apache-2.0"` (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui_windows/Cargo.toml and https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui_platform/Cargo.toml), so those resolve to `publish = false`. INFERENCE: the published `gpui` crate cannot depend on `gpui_platform` from crates.io, which is why gpui.rs tells users to add `gpui_platform` separately with `version = "*"` (VERIFIED, local `gpui_site_readme.md`). A consumer needs a git dependency on the Zed repo for the platform layer, a materially heavier posture than the other three.

**Windows backend: real, but with named gaps.** The `gpui_windows` crate is not a stub. Its module tree (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui_windows/src/gpui_windows.rs) includes `directx_renderer`, `directx_devices`, `directx_atlas`, `direct_write`, `direct_manipulation`, `clipboard`, `keyboard`, `display`, `events`, `vsync`, and `dialog`. The platform implementation is 73,591 bytes across 2,061 lines (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui_windows/src/platform.rs) with `impl Platform for WindowsPlatform` at line 536 and Windows Credential Manager at lines 1059 to 1130. The `windows` crate features include `Win32_Graphics_Direct3D11`, `Win32_Graphics_DirectComposition`, and `Win32_Graphics_DirectWrite` (VERIFIED, same Cargo.toml).

The gaps are explicit and bounded: `hide_other_apps` and `unhide_other_apps` are `unimplemented!()` with `// todo(windows)` markers, and `path_for_auxiliary_executable` bails with "not yet implemented" (VERIFIED, same platform.rs lines 712 to 719 and 999 to 1002). INFERENCE: these are macOS-specific platform-service APIs, not core rendering, input, or windowing, so they do not block a Slipstream console.

The upstream README, however, states plainly: "GPUI is still in active development as we work on the Zed code editor, and is still pre-1.0. There will often be breaking changes between versions" (VERIFIED, local `gpui_site_readme.md`, upstream https://gpui.rs). Verdict: the Windows backend is functional and substantial, but the framework around it is pre-1.0 and Zed-coupled. That is a real risk, not a blocker.

**Windows prerequisites.** VERIFIED (local `gpui_site_readme.md`, https://gpui.rs): "Windows: no features are required. Windowing uses Win32 and text uses DirectWrite. `font-kit` has no effect here." No WebView2, WebKitGTK, or OpenGL. INFERENCE: GPUI has the fewest external runtime dependencies of the four, but needs a D3D11-capable GPU and driver.

**Accessibility.** The upstream README links an "Accessibility" section on gpui.rs (VERIFIED, local `gpui_site_readme.md`, https://gpui.rs), and `gpui_windows` depends on `accesskit` and `accesskit_windows` (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui_windows/Cargo.toml). The rendered text was not retrievable in this pass, so the supported feature set is UNKNOWN, but the AccessKit integration is confirmed at the dependency level.

### iced

**License.** iced is MIT (VERIFIED, https://github.com/iced-rs/iced/blob/master/LICENSE; workspace `license = "MIT"` at https://raw.githubusercontent.com/iced-rs/iced/master/Cargo.toml line 173). VERIFIED from https://crates.io/api/v1/crates/iced: `max_stable_version` is `0.14.0`, description is "A cross-platform GUI library inspired by Elm", homepage `https://iced.rs`, 3,513,543 downloads.

**Windows support and prerequisites.** VERIFIED (https://github.com/iced-rs/iced README): "Cross-platform support (Windows, macOS, Linux, and the Web)" with two built-in renderers, `iced_wgpu` supporting "Vulkan, Metal and DX12" and `iced_tiny_skia` "offering a software alternative as a fallback." The crate features confirm both paths: `wgpu` (default) and `vello-cpu` as "the `vello-cpu` software renderer" (VERIFIED, https://raw.githubusercontent.com/iced-rs/iced/master/Cargo.toml lines 25 to 33). INFERENCE: iced is the only one of the four with a first-class, upstream-documented CPU rendering path, so it runs on a Steam Deck or a GPU-less VM without a graphics driver. Windowing is via winit.

**Accessibility.** UNKNOWN. Neither the iced README nor the crate manifest mentions accessibility, screen readers, or AccessKit. INFERENCE: iced 0.14 has no built-in accessibility layer, a material disadvantage against egui and GPUI.

## React reuse
None of the four can reuse React components, Tailwind classes, Storybook stories, or the orval-generated React Query client. That is a matter of category, not effort: none parses JSX, reads CSS, runs a DOM, or has a Storybook equivalent.

The rewrite cost is measured and large: 22,411 lines across 166 files and 789,847 bytes in `web/src`, of which `web/src/components` holds 28 files, 2,920 lines, and 106,259 bytes, plus 13 vendored design-system files. All are thrown away.

INFERENCE on relative speed: **egui** is fastest to prototype because it is immediate mode with no callback plumbing, its README calls it "the easiest-to-use Rust GUI library" (VERIFIED, local `egui_README.md`), and its non-goal of "Native looking interface" gives a consistent look immediately rather than fighting native theming. **Slint** has declarative markup that maps most naturally onto the React model plus a token-style theming system, but introduces a new language, build step, and editor toolchain. **iced** is Elm-like and type-safe, closest in spirit to React's component model, but experimental. **GPUI** is Zed's full framework and strongest for a large polished application, but pre-1.0 and Zed-coupled; its styling API is "tailwind-style" (VERIFIED, https://gpui.rs), the only partial bridge to Tailwind 4 tokens. For 16 feature sections, the fastest path to a usable native UI is egui and the highest ceiling is GPUI, but GPUI carries the most dependency and stability risk.

## Token and security

A native client has no browser. It calls the Rust management API directly over loopback HTTPS with the bearer token, removing a layer and changing the threat model. The current design, read from source:

- The BFF is the only LAN path to the management API. `web/server/routes/api/[...].ts` lines 1 to 5 state it "binds loopback only" and "this proxy is the ONLY path to it from the LAN, and it's authenticated."
- The bearer token never reaches the browser. It is injected server-side at `web/server/routes/api/[...].ts` lines 62 to 69: `authorization: Bearer ${token}`, with the browser cookie stripped via `cookie: ""`.
- TLS verification is relaxed for exactly one loopback hop, because the host presents a self-signed no-SAN cert: `web/server/routes/api/[...].ts` lines 56 to 60 set `tls: { rejectUnauthorized: false }` only when `isLoopbackUrl(base)` is true, and `web/server/util/auth.ts` lines 260 to 273 define that check as IPv4 127.0.0.0/8, IPv6 `::1`, and `localhost`.
- The console password session is sealed with a key derived by SHA-256 from the management token, labelled `slipstream-session-v1:token:${token}`, never the raw token (VERIFIED, `web/server/util/auth.ts` lines 289 to 307). The comment is explicit that this "turns any captured session cookie into an OFFLINE dictionary oracle."
- The console gate sets baseline headers and runs a mutating-request same-origin check: `web/server/middleware/auth.ts` lines 35 to 41 set `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and a CSP of `frame-ancestors 'self'; object-src 'none'; base-uri 'self'`. Lines 51 to 59 reject any non-GET/HEAD/OPTIONS request whose `Sec-Fetch-Site` header is present and not `same-origin` or `none`, returning 403 "cross-site request refused."
- First-run setup is loopback-only: `web/server/routes/_auth/setup.post.ts` lines 35 to 41 reject a non-loopback peer with 403 "first-time setup must be completed from the host"; `web/server/util/auth.ts` lines 101 to 102 define `isLoopbackAddress`.
- The plugin-ui per-boot secret is deliberately unreachable from a browser. `web/server/routes/api/[...].ts` lines 30 to 36 deny `/api/v1/plugins/{id}/ui-credential` with 403 "plugin UI credentials are not accessible from the browser," matching raw and normalised paths to defeat router quirks. The proxy fetches the credential server-side and injects it on the hop to `http://127.0.0.1:{cred.port}` (`web/server/routes/plugin-ui/[...].ts` lines 162 to 171), stripping `cookie`, `authorization`, and the capability header (same file lines 141 to 150).
**What disappears in a native client.** The `Sec-Fetch-Site` mutating-request check becomes dead code, since there is no browser to be ridden cross-site (VERIFIED as browser-specific at `web/server/middleware/auth.ts` lines 43 to 50). The CSP, `nosniff`, and `Referrer-Policy` headers apply to HTML responses and are irrelevant, as are the SameSite=Lax cookie attribute and the h3 session sealing. The 401-to-502 translation in `onResponse` (`web/server/routes/api/[...].ts` lines 76 to 82) becomes unnecessary because the client can read the real 401. The browser-facing `/login`, `/setup`, and `/_auth/` route surface disappears, along with `isPublicPath` (`web/server/util/auth.ts` lines 343 to 354).

**What must be added.** INFERENCE: a native client must implement its own credential storage. The bearer token must live in the OS credential store or an equivalently protected file and must never be logged. The console-password prompt moves in-process, replacing the cookie-sealed session with a native secret store. The first-run loopback-only setup rule must be reimplemented by peer-address check. The plugin-ui per-boot secret must be fetched by the native client and held in memory only, since the denylist at `web/server/routes/api/[...].ts` lines 30 to 36 protected it from a *browser* and a native client has no equivalent boundary. The strongest simplification is that the direct loopback HTTPS call with the bearer token removes the entire BFF, session layer, and CSRF defence, but it also removes the boundary keeping the plugin secret out of untrusted UI code.

## Polish effort

No CSS, no Tailwind pipeline, no Storybook, no DOM, no browser text rendering. Typography, spacing, and colour become toolkit-native concerns.

egui: styling is `Context::set_style` for "the colors, spacing, fonts and sizes of everything," and the README is blunt that this "is not yet as powerful as say CSS" (VERIFIED, local `egui_README.md`). Fonts must be supplied by the app for non-Latin characters (`Context::set_fonts`). INFERENCE: the visual identity must be rebuilt as Rust style constants, and the 13 vendored design-system files have no mechanical conversion.

Slint has a proper styling system with properties and a token-like theme concept, plus the `AboutSlint` attribution widget the licence requires anyway. GPUI styles views through "a tailwind-style API" (VERIFIED, https://gpui.rs), the closest conceptual match to the existing Tailwind 4 vocabulary, though tokens must still be re-declared. iced has a type-safe Elm-like model with no documented theming layer.

Accessibility, honestly. egui has the strongest story: AccessKit is enabled by default in eframe on Windows and macOS, with an experimental built-in screen reader elsewhere (VERIFIED, local `egui_README.md` and https://github.com/emilk/egui/blob/main/docs/accessibility.md). GPUI depends on `accesskit` and `accesskit_windows` (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui_windows/Cargo.toml) and upstream links an accessibility section on gpui.rs, but the feature set is UNKNOWN. Slint exposes an `accessibility` feature (VERIFIED, https://crates.io/api/v1/crates/slint), per-platform coverage UNKNOWN. iced has no documented accessibility support: UNKNOWN, and that absence is itself the finding. For 16 feature sections, egui's default-on AccessKit plus `egui_kittest` role-based testing is the only path where accessibility is regression-tested rather than asserted.

## Distribution

Windows without admin rights is the requirement. None of the four needs admin to run; only packaging differs.

Slint's documented Windows packaging is MSIX (VERIFIED, https://docs.slint.dev/latest/docs/slint/guide/platforms/desktop/packaging/windows/), which needs the Windows SDK, `makeappx`, `makepri`, an `AppxManifest.xml` with `runFullTrust` and `EntryPoint="Windows.FullTrustApplication"`, and icon variants from 16 to 256 pixels. MSIX also installs the Visual C++ runtime as a framework dependency. The same page notes MSIX "works outside the Store" but that WiX, Inno Setup, NSIS, and a plain `.zip` are all valid and outside Slint's documented scope. INFERENCE: MSIX is the wrong target for a no-admin, per-user install because it registers through the deployment service and can behave differently under device policies. A ZIP or Inno Setup installer is correct, and neither is Slint-specific.

There is no first-party Slipstream winget package anywhere. VERIFIED: the winget-pkgs manifest listings at https://github.com/microsoft/winget-pkgs/tree/master/manifests/m and https://github.com/microsoft/winget-pkgs/tree/master/manifests/s contain no Slipstream entry (the only near-matches are MoonlightGameStreamingProject under `m` and seven `Stream*` packages under `s`), and `manifests/m/Slipstream` returns 404.

A new winget package would require (VERIFIED, https://cdn.jsdelivr.net/gh/microsoft/winget-pkgs@master/doc/Authoring.md): a unique `PackageIdentifier` in `Publisher.Package` form; a multi-file manifest with at minimum a version directory and an installer file; a layout partitioned by the lowercase first letter of the identifier then each case-sensitive segment; a check for existing packages and PRs before submission; and a stable installer URL. The guide recommends `winget-create`, which "guides you through the process and validates your manifest," and `winget validate --manifest <path>` validates a manifest locally before submission (VERIFIED, https://learn.microsoft.com/en-us/windows/package-manager/winget/validate). On submission, a GitHub App runs the Validation Pipeline on the manifest and installers and reports on the PR (VERIFIED, same authoring guide). INFERENCE: winget is a distribution-channel project, not a UI-technology decision, and should be sequenced after a native client ships a stable signed installer URL.

## Cross-platform: Linux and Steam Deck

SteamOS is Linux, so Linux support is prerequisite for any Deck story.

**Slint.** VERIFIED (https://docs.slint.dev/latest/docs/slint/guide/platforms/desktop/linux/general/): Slint "should run on any of them, provided that they are using Wayland or X11, glibc, and D-Bus." The winit backend requires X11 or Wayland at runtime, with X11 client packages libx11-xcb, xinput, libxcursor, libxkbcommon-x11, and libx11 (VERIFIED, https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backend_winit/). The linuxkms backend needs no windowing system or compositor (VERIFIED, same backends page), a Deck-friendly embedded-display path, and `renderer-software` removes the GPU requirement entirely (VERIFIED, same page).
**egui / eframe.** Linux needs system packages for the demo app: `libclang-dev libgtk-3-dev libxcb-render0-dev libxcb-shape0-dev libxcb-xfixes0-dev libxkbcommon-dev libssl-dev` on Debian-family systems, or the Fedora equivalent (VERIFIED, local `egui_README.md`). The README notes "egui itself is completely platform agnostic"; the demo deps are the winit/GTK layer. INFERENCE: a packaged egui app needs the X11/Wayland client libraries present, which SteamOS ships.

**GPUI.** VERIFIED (https://gpui.rs): "Linux / FreeBSD: enable at least one windowing backend for desktop windows: `wayland`, `x11`, or both." The crate features confirm `wayland` and `x11` are default-enabled, and the target-specific dependency block covers `cfg(any(target_os = "linux", target_os = "freebsd"))` with ashpd, calloop, cosmic-text, font-kit, x11rb, xkbcommon, and the wayland client crates (VERIFIED, https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui/Cargo.toml and the crates.io feature list).

**iced.** VERIFIED (https://raw.githubusercontent.com/iced-rs/iced/master/Cargo.toml): default features include `x11`, `wayland`, `wayland-dlopen`, and `wayland-decorations`, with `linux-theme-detection` for system theme following. The `vello-cpu` software renderer is a default feature, making iced the most Deck-tolerant of the four graphics-wise.

**Steam Deck specifically.** UNKNOWN for all four. No primary source in the local `steamdeck.md`, `steam_deck_faq.html`, `steam_linux_runtime.html`, or `steam_sos.html` files, nor the upstream projects' documentation, covers running a native management console on SteamOS, its Desktop Mode, or its gaming mode. INFERENCE: Deck support needs separate verification against Deck-specific GPU driver behaviour and Desktop Mode's compositor, and should be an open item rather than inferred from Linux support.

## Recommendation

INFERENCE: **egui/eframe** is the lowest-risk choice on licensing (MIT OR Apache-2.0, no obligations), Windows maturity ("should work out-of-the-box on Mac and Windows"), and accessibility (AccessKit on by default in eframe on Windows, with `egui_kittest` role-based regression testing). It is also the fastest to prototype against 16 feature sections. Its two real costs are the visual rebuild (no CSS pipeline; `Context::set_style` is explicitly weaker than CSS) and no documented software-rendering fallback, which matters for a GPU-less target.

**Slint** is the strongest second choice, and the only one whose license explicitly permits closed-source shipping at no cost and no revenue threshold under Royalty-free. It also has the only documented no-GPU path (`winit-software`) and a no-windowing-system path (linuxkms).

**GPUI** has the highest ceiling and the closest styling analogue to the existing Tailwind tokens, but it is pre-1.0, Zed-coupled, and its platform layer is not on crates.io, making its dependency posture heavier than the other three.

**iced** is the weakest fit, with no documented accessibility support and an explicit "experimental software" label, despite the best software-rendering story.
