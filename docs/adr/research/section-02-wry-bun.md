## Option 2: wry used directly, and a Bun-compiled executable

This section separates two ideas that are often conflated. The first is a native window that hosts the existing React console through wry without adopting Tauri. The second is a desktop shell delivered as a Bun-compiled executable, which changes what runs on the end-user machine rather than how the webview is created.

### 2a. wry used directly

wry is the Rust webview library that Tauri is built on. Its repository describes it as a "Cross-platform WebView library in Rust for Tauri" (https://github.com/tauri-apps/wry). Tauri's own documentation states that TAO is responsible for Tauri window creation and WRY is responsible for webview rendering, and that both libraries can be consumed directly when deeper system integration is required outside what Tauri exposes (https://v2.tauri.app/start/). The wry v0.58.1 crate metadata declares `license = "Apache-2.0 OR MIT"`, VERIFIED (https://github.com/tauri-apps/wry/blob/wry-v0.58.1/Cargo.toml), and the repository page lists both Apache-2.0 and MIT license files (https://github.com/tauri-apps/wry). INFERENCE: For a project that needs a branded native window, the license imposes no commercial royalty and no GPL obligation (https://github.com/tauri-apps/wry/blob/wry-v0.58.1/Cargo.toml).

Using wry directly is a lower-level exercise than using Tauri. wry requires a running event loop and a window type that implements `HasWindowHandle`, or a GTK container widget when supporting X11 and Wayland (https://github.com/tauri-apps/wry). INFERENCE: that is a library contract, not an application framework, so the application owns window lifecycle, event loop integration, and webview teardown.

What hand-rolled wry does not give you is the rest of Tauri (https://v2.tauri.app/). The Tauri CLI builds release binaries and generates bundles and installers (https://v2.tauri.app/reference/cli/). The Tauri configuration object defines frontend assets, the bundler, security settings, windows, and a tray icon (https://v2.tauri.app/reference/config/). Tauri IPC supplies asynchronous message passing with Events and Commands, including the `invoke` primitive (https://v2.tauri.app/concept/inter-process-communication/). The updater plugin verifies signed update artifacts and generates signed bundles for Windows, macOS, and Linux (https://v2.tauri.app/plugin/updater/). Permissions describe explicit privileges and are granted to windows or webviews through capabilities (https://v2.tauri.app/security/permissions/). The single-instance plugin ensures only one app instance runs and can focus the existing window (https://v2.tauri.app/plugin/single-instance/). Tray support is part of the configuration surface (https://v2.tauri.app/reference/config/). INFERENCE: a hand-rolled wry shell must either implement or consciously omit each of these, which turns a framework purchase into several small projects.

The Linux dependency situation is the hard part. wry v0.58.1 pins `webkit2gtk = "3"` with the `v2_38` feature, `webkit2gtk-sys = "3"`, `gtk = "0.19.0"`, and `soup3 = "0.9.0"` under its Linux target dependencies, and the `os-webview` feature enables those crates, VERIFIED (https://github.com/tauri-apps/wry/blob/wry-v0.58.1/Cargo.toml). wry's README says Linux uses WebKitGTK and requires GTK, and that a GTK container is needed to support both X11 and Wayland (https://github.com/tauri-apps/wry). INFERENCE: Those pins are the same dependency wall Tauri hits (section-01-tauri.md:91), so choosing raw wry does not escape them.

On Windows the webview is WebView2 provided by Microsoft Edge Chromium, and wry's own compatibility statement covers Windows 7, 8, 10, and 11 (https://github.com/tauri-apps/wry). Microsoft says WebView2 apps can run on Windows 10 variants and Windows 11 (https://learn.microsoft.com/en-us/microsoft-edge/webview2/), that the Evergreen Runtime is preinstalled on all Windows 11 devices and was installed on all eligible Windows 10 devices, and that some devices might not have it preinstalled (https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). Prior research for this decision records it as present on Windows 11 and Windows 10 version 2004 and later, with a separate install needed on older Windows 10 (section-01-tauri.md:15 and docs/adr/0001-desktop-dashboard-framework.md:357-358). Microsoft recommends that developers distribute the Runtime to cover edge cases (https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/evergreen-vs-fixed-version).

INFERENCE: React reuse is unchanged because wry navigates a webview to the same asset bundle that Tauri would serve, so the existing React console, its Vite output, the design system, and the orval-generated client remain the UI. INFERENCE: The webview host changes, the UI code does not.

INFERENCE: Option 2a is only attractive if the team specifically wants direct control over window and webview plumbing and is willing to rebuild the framework services it omits. For Slipstream, that means paying Tauri's dependency and Deck costs while giving up the bundler, config, IPC, updater, permissions, single-instance handling, and tray that make Tauri worth considering in the first place.

### 2b. A Bun-compiled executable

The URL named in the brief, https://bun.sh/docs/bundler/executables, returned HTTP 404 when fetched. The current official documentation is https://bun.sh/docs/compiler/executables.md, which is the source used below. Claims not present on that page are marked UNKNOWN.

`bun build --compile` generates a standalone binary from a TypeScript or JavaScript file (https://bun.sh/docs/compiler/executables.md). Bun bundles all imported files and packages into the executable along with a copy of the Bun runtime, and all built-in Bun and Node.js APIs are supported (https://bun.sh/docs/compiler/executables.md). A compiled executable can embed both server and client code, including HTML, CSS, JavaScript, npm packages, and the Bun runtime, into a single file that serves frontend assets with MIME types and cache headers (https://bun.sh/docs/compiler/executables.md).

The documented `--target` values are `bun-linux-x64`, `bun-linux-arm64`, `bun-windows-x64`, `bun-windows-arm64`, `bun-darwin-x64`, `bun-darwin-arm64`, `bun-linux-x64-musl`, and `bun-linux-arm64-musl` (https://bun.sh/docs/compiler/executables.md). On x64, Bun ships one binary targeting Nehalem with SSE4.2 and selects AVX2 or AVX-512 paths at runtime, and the older `-baseline` and `-modern` suffixes resolve to the same binary (https://bun.sh/docs/compiler/executables.md). Windows output gets an `.exe` extension automatically when none is supplied (https://bun.sh/docs/compiler/executables.md).

The documented limitations matter. Compiled executables disable `tsconfig.json` and `package.json` autoloading by default while enabling `.env` and `bunfig.toml`, with a note that the latter may also be disabled in a future version (https://bun.sh/docs/compiler/executables.md). Workers must be listed as entrypoints, and a relative path not included in the executable is loaded from the process working directory and errors if absent (https://bun.sh/docs/compiler/executables.md). SQLite imports resolve relative to the current working directory by default (https://bun.sh/docs/compiler/executables.md). Embedded files are read-only and writes fail with `EROFS` (https://bun.sh/docs/compiler/executables.md). Ahead-of-time compilation via `bun compile` is experimental, and `--trim` is experimental (https://bun.sh/docs/compiler/executables.md). Except for `--windows-hide-console`, Windows metadata flags cannot be used when cross-compiling (https://bun.sh/docs/compiler/executables.md).

Does the compiled binary remove the need to install Bun on the end-user machine? Yes. Bun's docs describe the full-stack result as a single file deployable anywhere without installing Node.js, Bun, or any dependencies (https://bun.sh/docs/compiler/executables.md). INFERENCE: that answers the end-user runtime question for the server side, but it does not create a native window by itself.

Whether a Bun shell replaces the nitro server is the consequential question. The existing route file is an h3 handler, importing `proxyRequest` and `defineEventHandler` from `h3` (web/server/routes/api/[...].ts:6-12). By the time it runs, middleware has confirmed an authenticated session, and the handler injects the management bearer token server-side so the browser never sees it (web/server/routes/api/[...].ts:1-5). It denies normalized and raw paths that would expose a plugin UI credential with a 403 (web/server/routes/api/[...].ts:20-36). It reads the management URL and token, returns 503 when no token is configured, and proxies to the loopback management API (web/server/routes/api/[...].ts:37-49). TLS verification is relaxed only for the loopback hop through a Bun-specific per-request `tls` option, and a non-loopback management URL must present a valid chain (web/server/routes/api/[...].ts:50-60). The proxy overwrites the authorization header with the host token, clears the browser cookie, and converts an upstream 401 into a 502 so a logged-in user is not bounced into a redirect loop (web/server/routes/api/[...].ts:62-84). INFERENCE: if `Bun.serve` replaces nitro and h3, every one of those behaviors must be reimplemented in Bun, including the auth gate, path normalization, credential denylist, token injection, cookie stripping, scoped TLS relaxation, and 401 mapping. `Bun.serve` route support is documented (https://bun.sh/docs/compiler/executables.md), but this specific proxy is UNKNOWN in Bun form because no such implementation was provided.

Size and footprint are only partly documented. Bun says a standalone executable is a copy of the Bun runtime with the program attached, that a small program is almost all Bun, that compiled executables reduce memory usage and improve start time, and that `--trim` removes unused Bun and Node APIs (https://bun.sh/docs/compiler/size.md and https://bun.sh/docs/compiler/executables.md). Bun also says its binary is "still way too big" and that reducing it is ongoing work (https://bun.sh/docs/compiler/executables.md). A specific byte size or resident memory figure for a Slipstream console binary is UNKNOWN because no cited primary source gives one.

### 2c. Cross-cutting

Token and security. Under 2a the token position is unchanged only if the wry webview points at the existing nitro server on its loopback origin. Prior research establishes that pointing the webview at `http://127.0.0.1:47992` keeps relative `/api/...` calls on the same origin as the BFF proxy and leaves the bearer token server-side (section-01-tauri.md:47). INFERENCE: a wry webview loaded from a different origin would either break relative API calls or tempt a redesign that moves the token into the renderer. Under a `Bun.serve` replacement the proxy must be reimplemented in Bun, because the current token injection, cookie stripping, and credential denylist live in the h3 handler (web/server/routes/api/[...].ts:1-5 and web/server/routes/api/[...].ts:62-84). INFERENCE: any rewrite is a security-sensitive change, not a packaging detail.

Steam Deck. The Steam Linux Runtime ships no WebKitGTK in any of its four current branches, with `soldier`, `sniper`, `steamrt4`, and `steamrt5` ABI expectation manifests containing no webkit2gtk entry, VERIFIED in prior research (section-01-tauri.md:97). wry v0.58.1 links WebKitGTK and GTK on Linux (https://github.com/tauri-apps/wry/blob/wry-v0.58.1/Cargo.toml), so a wry webview cannot ship to the Deck as a Steam Runtime title today (section-01-tauri.md:109). For 2a the consequence is disqualifying if Deck support is a firm requirement. INFERENCE: a Bun-compiled binary has no GTK or WebKitGTK dependency, so it sidesteps that specific blocker, though a Bun binary still needs some way to present a graphical console, and that mechanism is UNKNOWN here.

Distribution without admin rights on Windows. The ADR constraint requires Windows artifacts installable without admin rights via winget, scoop, msix, or a portable zip (docs/adr/0001-desktop-dashboard-framework.md:47). WinGet can run without administrator privileges, but some applications require elevation and will prompt for it, so no-admin behavior is package dependent (https://learn.microsoft.com/en-us/windows/package-manager/winget/). Tauri's NSIS installer installs for the current user by default and does not require Administrator privileges, with `perMachine` requiring elevation (https://v2.tauri.app/distribute/windows-installer/). Scoop's no-admin property could not be verified because https://scoop.sh/ returned no content on fetch, so that claim is UNKNOWN. Portable zip behavior for this project is UNKNOWN without a cited source. There is no first-party Slipstream installer in the repository today (docs-site/content/docs/windows-host.md:13), so no first-party Slipstream package exists in winget or scoop today based on the evidence available here, which is UNKNOWN beyond that repository statement.

### 2d. Verdict

INFERENCE: Option 2a is not worth pursuing on its own because it inherits every wry dependency and Deck failure while dropping the framework services that make a native shell economical. INFERENCE: Option 2b is worth a bounded proof of concept only if the operator wants a branded native app and accepts reimplementing the security proxy, because it removes the end-user Bun install and sidesteps WebKitGTK. INFERENCE: Without that branding requirement, neither sub-option beats keeping the web app and serving it locally.
