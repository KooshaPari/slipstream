## 4. Environment facts established this session

- **CMake cannot build cmake-based crates as-is.** CMake here is 4.0.3; only Visual Studio Build
  Tools 2026 (VS 18) is installed; `cmake-rs` asks for the `Visual Studio 17 2022` generator, which
  cannot find an instance, and CMake 4.0.3 has no VS 18 generator. Working recipe (documented in the

  `CMAKE_POLICY_VERSION_MINIMUM=3.5` and `CMAKE_GENERATOR_x86_64-pc-windows-msvc=Ninja`, and delete

  500,000,000,000 threshold in both directions. It must not be reported as a rate, a trend, or a
  leak. Several peer heartbeat lanes carry the same standing correction.
- **Installed layout is split.** Host under `%ProgramFiles%`, tray autostart pointing into
  `%LOCALAPPDATA%`, for the reason now documented.

## 7. c3-console closed, and a correction to section 6

`tailscale serve status` resolves what port 8446 actually is:

```
https://<tailnet-hostname>:8446 (tailnet only)
|-- / proxy https+insecure://127.0.0.1:47992
```

So 8446 is the console, published by Tailscale Serve in front of the real console on 47992. Requests
to the bare tailnet IP return HTTP 400 because Serve routes by hostname, and loopback is refused by
design. The goal's literal check therefore passes when addressed correctly:

- `https://<tailnet-hostname>:8446/login` returned **200**.

Recovery after a supervisor death is not merely predicted, it is **observed**. The supervisor log at
`%LOCALAPPDATA%\slipstream\logs\slipstream-web.log` records three separate supervisor restarts,
each bringing the console back to a listening state:

```
[2026-11-25 00:35:43] supervisor started pid=2624  -> listening on https://0.0.0.0:47992/ (tls=true)
[2026-11-25 17:04:16] supervisor started pid=15116 -> listening on https://0.0.0.0:47992/ (tls=true)
[2026-11-26 20:47:12] supervisor started pid=14136 -> listening on https://0.0.0.0:47992/ (tls=true)
```

`SlipstreamWebWatchdog` repeats every 1 minute (`interval=PT1M`), so any kill self-heals within about
a minute. I did not kill anything to prove this, because the log already contains the proof three
times over.

**Correction to section 6, point 3.** I wrote that `C:\Program Files\Slipstream` "is not what runs"
and is not executed by any task. That is wrong. The *host* does not run from there, but
`supervise-slipstream-web.ps1` sets `$programDir = 'C:\Program Files\Slipstream'` and launches
`slipstream-web.cmd` from that directory. So Program Files is live and must keep `slipstream-web.cmd`
and `slipstream.ico`. What is stale there is only the host binary and the client binary.
